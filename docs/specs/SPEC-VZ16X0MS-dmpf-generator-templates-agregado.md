# SPEC-VZ16X0MS: DMPF KRN-12.2b — Templates por agregado nos cinco blocos

## Resumo

> **Deferida em 2026-09-09.** O generator orientado ao domínio foi preterido pelo
> caminho híbrido AI SDD: esqueleto determinístico pelo generator existente e
> código de negócio escrito por agentes a partir da spec do bounded context
> (`SPEC-SPEC-VDP9XX65`). Esta spec fica como caminho avaliado — duas revisões
> externas (24 achados) documentam o custo do determinístico — e pode ser
> retomada se a geração por agentes não sustentar os gates.

Segunda sub-spec da reescrita do generator `bounded-context`: os templates Go
deixam de descrever `Request`/`Fulfillment` e passam a ser **parametrizados
pelo `DomainModel`** (SPEC-8FSD8505). Para cada agregado da definição, o
generator produz nos cinco blocos o que é mecânico — agregado com snapshot,
uma UPR por comando, eventos, códigos de rejeição das invariantes declaradas,
`Resources` e `Reader`, um caso de uso por comando com os nove passos de
FND-04 §3.2, uma consulta por `query`, tabela e repositório Postgres, uma rota
HTTP por comando e o OpenAPI correspondente — e deixa como stub protegido só o
que é regra de negócio. O gerado importa o kernel (`dmpfdomain`, `dmpfports`,
`dmpfapplication`, providers, kits), o que exige o shared kernel
(SPEC-XMNBMY50) para ser aprovado pelo verificador.

Como squad, quero que `bookings.jsonc` vire `Booking`, `Reserve`, `Cancel`,
`BookingReserved`, `bookings_booking` e `POST /bookings/booking/{id}/reserve` — e que o
que sobra para eu escrever seja a regra dentro de `Reserve`.

## Contexto

## Design

### Arquitetura

```text
 DomainModel ──► por bloco ──► perModule templates ─────────────────────────┐
                           ├─► perAggregate × aggregates ──► writer(mecânico) ─┤
                           ├─► perCommand × commands ──► writer(mecânico) ──────┤──► módulo <ctx>-<sufixo>
                           ├─► perCommand rules ──► writer(stub, só se ausente) ┤
                           ├─► perQuery × queries ──► writer(mecânico) ─────────┤
                           └─► perConsume × consumes ──► writer(mecânico+stub) ─┘
 domain: só dmpfdomain + stdlib permitida pelo depguard; nada de porta/relógio/wire
```

### Fluxo principal

1. O generator (SPEC-8FSD8505) entrega o `DomainModel` de `bookings.jsonc`.
2. `blocks.ts` lista, por bloco, os templates e a cardinalidade (módulo,
   agregado, comando, consulta, consumo) e o tipo (mecânico ou stub).
3. O `writer` grava; o `doc.go` de cada package e o `README.md` do módulo
   listam agregados e packages.
4. A prova gera, classifica, commita e roda a cadeia; o verificador aprova
   porque `dmpf-kernel` é shared kernel.

### Pseudocódigo (UPR gerada, comando com `effects` declarados)

```text
func Reserve(b Booking, cmd ReserveCommand, at Instant) (Accepted[ReserveResponse], *Rejection) {
  // preconditions do comando (mecânico) — range(cmd.quantity, 1, 100)
  if cmd.Quantity < 1 || cmd.Quantity > 100 { return reject(CodeQuantityOutOfRange, ...) }
  // regra do usuário (stub protegido reserve_rules.go) — só rejeição quando há effects
  if rej := reserveRules(b, cmd, at); rej != nil { return reject(rej) }
  // effects e bindings declarados (mecânico): status=reserved, quantity=cmd.quantity, resourceId=cmd.resourceId, reservedAt=at
  next := b.clone(); next.status = Reserved; next.quantity = cmd.Quantity; next.resourceID = cmd.ResourceID; next.reservedAt = at
  // response e eventos pelos bindings from (mecânico)
  return accept(next, ReserveResponse{BookingID: next.id}, BookingReserved{BookingID: next.id, ResourceID: next.resourceID, Quantity: next.quantity, At: at})
}
// comando SEM effects: o stub devolve (next, response, events, *Rejection) e a UPR gerada só aplica preconditions e embrulha.
```

## Decisões técnicas

- **Transição declarativa quando há `effects`, stub completo quando não há**
  porque o generator não pode inventar o que a definição não diz: sem `effects`
  o mecânico não sabe qual campo muda nem como montar evento e resposta.
  Alternativa descartada: mecânico sempre com transição "óbvia", porque o
  trecho inventaria `status = Reserved` a partir de nada.
- **Regra do usuário num arquivo à parte (`<command>_rules.go`)** porque a
  fronteira é por arquivo; misturar regra gerada e escrita no mesmo arquivo
  impediria a regeneração. Alternativa descartada: marcadores de
  região, porque exigem merge textual e nenhuma ferramenta do workspace os
  reconhece.
- **Pré-condições e efeitos declarados viram código e teste** porque são as
  únicas regras que o generator conhece com precisão; o teste gerado cobre
  exatamente o que a definição declara, e o `_rules` fica sem teste gerado (é
  do usuário). Pré-condições pertencem ao comando, não ao agregado: uma
  regra de `Cancel` não pode aparecer em `Reserve`.
- **Uma tabela por agregado com `snapshot jsonb` e colunas só para consultas
  e relações, com índice composto por consulta** porque preserva a forma dos
  repositórios existentes (ADR-035) sem fixar o esquema relacional do estado;
  campos que não participam de consulta não precisam de coluna, e uma
  consulta por vários campos precisa de um índice que os cubra juntos. Alternativa descartada: uma
  coluna por campo, porque toda mudança de campo viraria migração.
- **Rota por comando, não por recurso REST genérico** porque a UPR é o
  contrato (FND-06 §9: POST com chave de idempotência para criação, comando
  nomeado no caminho); `PATCH` nunca (RST-02).

## Escopo fora

- **Payload protobuf dos integration events, `.proto`, rito Buf, wiring da
  outbox/inbox com o contrato**: `SPEC-F7S5B6KV`.
- **Composition root (`cmd/` com `--role`)**: continua fora; cabear processo é
  copiar `dmpf-reference` (golden path).

  subconjunto `by[]`/`returns`; são código do usuário no `Reader`.

  estado atual; evoluir tabela existente é do usuário.
